# 001 · Base del proyecto: monorepo, multitenancy y aislamiento entre empresas

- **Historias y requerimientos:** RF-01 y RF-02 (modelo de datos y servicios; sus pantallas y endpoints de plataforma llegan con la autenticación), RNF-06, RNF-17. Relacionadas: HU-01 (parcial: la suscripción de la sucursal es RF-03), RNF-09 (auditoría de las operaciones de plataforma).
- **Ruta crítica:** sí (confirmado por el usuario). Implementa el aislamiento entre empresas (RLS), que es el primer punto de la lista de ruta crítica de `CLAUDE.md`.
- **Estado:** aprobada

## Objetivo

Dejar la base técnica sobre la que se construye todo lo demás: el monorepo, la API en NestJS con PostgreSQL, las tablas de plataforma (empresa, emisor y sucursal) y, sobre todo, la garantía de que una empresa nunca ve, modifica ni crea datos de otra. La garantía la da la base de datos (RLS) y la refuerza la API: sin contexto de empresa, las consultas fallan. También deja preparado el punto donde la historia 002 (autenticación) fijará la empresa de cada petición, y una vía explícita y auditada para las operaciones de plataforma que no tienen empresa.

## Glosario

- **Contexto de empresa:** la empresa a la que pertenece la operación en curso. Vive en el `AsyncLocalStorage` de la petición y, dentro de la base, en la fila de la sesión en la tabla interna `contexto.sesion_empresa`, atada a la transacción en curso. Se fija una sola vez por transacción con `fijar_contexto_empresa` y la RLS lo lee con `empresa_actual()` (criterio 22e). El parámetro `app.empresa_id` queda solo como copia para diagnóstico: la RLS no lo lee.
- **Tabla de empresa:** tabla con datos de clientes. Lleva `empresa_id` (salvo `empresa`, cuyo `id` es la propia empresa), RLS activada y forzada, y la política estándar.
- **Operación de plataforma:** operación del superadministrador que no pertenece a una empresa (por ejemplo, dar de alta una empresa). Corre con un rol de base distinto y deja una fila en la auditoría de plataforma.
- **Roles de base de datos:** `restaurante_migrador` (dueño de las tablas, solo migraciones), `restaurante_api` (la API, sujeta a RLS) y `restaurante_plataforma` (operaciones de plataforma, sujeta a sus propias políticas). Ninguno es superusuario ni tiene `BYPASSRLS`.

## Criterios de aceptación

Salvo que se diga otra cosa, los escenarios de aislamiento parten de dos empresas, **A** y **B**, cada una con al menos un emisor y dos sucursales, creadas con la vía de plataforma. "Conectado como `restaurante_api`" significa una conexión directa a PostgreSQL con ese rol, sin pasar por la API. A nivel de SQL, "con el contexto de A" significa que la transacción en curso ejecutó `SELECT fijar_contexto_empresa(<id de A>)` (criterio 22e); por la API, que el código corre dentro de `ContextoEmpresa.ejecutar(A)`, que lo fija así.

### Monorepo, entorno local y CI

1. Dado un clon limpio con Node 22 y pnpm 10, cuando se ejecutan `pnpm install --frozen-lockfile`, `pnpm lint`, `pnpm typecheck` y `pnpm test` (este último con `DATABASE_ADMIN_URL` apuntando a un PostgreSQL 16), entonces los cuatro terminan sin errores.
2. Dado un equipo con Docker y sin PostgreSQL propio, cuando se ejecuta `pnpm local:preparar`, entonces queda un PostgreSQL 16 en marcha con los tres roles, la base `restaurante` migrada y los datos de demostración (dos empresas); y `pnpm dev` levanta la API en el puerto 3000 con `GET /health` respondiendo 200. Esto vale en un clon limpio, recién instalado y sin compilar nada antes: `pnpm local:preparar` compila los paquetes compartidos (`packages/dominio` y `packages/contratos`) antes de correr la semilla. El README (y `.env.example`, que `local:preparar` copia a `.env` si falta) da todas las variables que `pnpm dev` necesita, incluido `NODE_ENV` (criterio 29b).
3. Dado un PostgreSQL 16 sin Docker (entorno en la nube) y `DATABASE_ADMIN_URL` con un usuario administrador, cuando se ejecutan `pnpm db:preparar`, `pnpm db:migrar` y `pnpm db:semilla`, entonces el resultado es el mismo que en el criterio 2. Ejecutar de nuevo `db:preparar` y `db:migrar` no falla ni duplica nada. La secuencia nativa que da el README también funciona en un clon limpio: compila los paquetes compartidos antes de la semilla (como paso propio o dentro de `db:semilla`), y el README indica todas las variables necesarias para esos comandos y para `pnpm dev`.
4. Dado un push o un pull request en GitHub, cuando corre el workflow de CI, entonces instala dependencias, ejecuta lint, verificación de tipos y pruebas contra un servicio PostgreSQL 16, y el workflow falla si falla cualquiera de esos pasos.

### Salud

5. Dada la base disponible, cuando se llama `GET /health` sin cabeceras ni contexto de empresa, entonces responde 200 con `{ "estado": "ok", "baseDeDatos": "ok" }`.
6. Dada la base inaccesible (apagada o con credenciales inválidas), cuando se llama `GET /health`, entonces responde 503 con `{ "estado": "error", "baseDeDatos": "error" }` en menos de 3 segundos, sin incluir el mensaje del error ni datos de conexión.

### Roles de la base de datos

7. Dados los roles creados por `db:preparar`, cuando se consultan sus atributos, entonces `restaurante_api` y `restaurante_plataforma` no son superusuarios, no tienen `BYPASSRLS`, `CREATEROLE` ni `CREATEDB`, no son dueños de ninguna tabla ni función y no son miembros de `restaurante_migrador` ni entre sí; `restaurante_migrador` tampoco es superusuario ni tiene `BYPASSRLS`.
8. Dado `restaurante_api` conectado, cuando intenta `ALTER TABLE sucursal DISABLE ROW LEVEL SECURITY`, `ALTER TABLE sucursal NO FORCE ROW LEVEL SECURITY`, `DROP POLICY`, `CREATE POLICY`, `SET ROLE restaurante_migrador`, `TRUNCATE sucursal`, crear una tabla o una función en `public`, o crear una tabla temporal, entonces cada intento falla con un error de permisos.
9. Dado `restaurante_api` conectado con contexto de la empresa A, cuando ejecuta `SET row_security = off` y luego `SELECT * FROM sucursal`, entonces la consulta falla (no devuelve filas de ninguna empresa).
10. Dada una `DATABASE_URL` (o `DATABASE_PLATAFORMA_URL`) cuyo rol es superusuario, tiene `BYPASSRLS` o es dueño de alguna tabla de `public`, cuando arranca la API, entonces no arranca y el registro indica qué rol y qué atributo lo impiden.

10b. **Membresías al arrancar.** Dada una `DATABASE_URL` (o `DATABASE_PLATAFORMA_URL`) cuyo rol es miembro, directo o transitivo (a través de cualquier cadena de `GRANT rol TO rol`) y sea la membresía con `INHERIT` o con `NOINHERIT`, de `restaurante_migrador`, del dueño de alguna tabla de `public`, o de un rol superusuario o con `BYPASSRLS`, cuando arranca la API, entonces no arranca y el registro indica el rol conectado y la membresía que lo impide (el rol del que es miembro y el motivo). Esto hace verificable al arrancar lo que el criterio 7 exige a los roles creados por `db:preparar`. Los roles que deja `db:preparar` (criterio 7) arrancan sin problema.

### Aislamiento entre empresas

11. **Lectura por id.** Dado el contexto de A, cuando se lee la sucursal o el emisor de B por su id (SQL directo como `restaurante_api` y `SucursalService.obtener`), entonces no se obtiene ninguna fila; el servicio responde lo mismo que para un id inexistente.
12. **Listados.** Dado el contexto de A, cuando se listan `empresa`, `emisor` y `sucursal` sin filtros, entonces solo aparecen filas de A (en `empresa`, solo la fila de A).
13. **Actualización.** Dado el contexto de A, cuando se ejecuta un `UPDATE` sobre la sucursal de B por id, y otro `UPDATE` sin `WHERE`, entonces el primero afecta 0 filas, el segundo solo afecta filas de A, y las filas de B quedan idénticas.
14. **Cambio de dueño.** Dado el contexto de A, cuando se actualiza una sucursal o un emisor de A con `empresa_id` = B, entonces la sentencia falla y la fila no cambia.
15. **Borrado.** Dado el contexto de A, cuando se ejecuta un `DELETE` de la sucursal de B por id, y otro `DELETE` sin `WHERE` (dentro de una transacción que luego se revierte), entonces el primero afecta 0 filas y el segundo solo afecta filas de A.
16. **Inserción ajena.** Dado el contexto de A, cuando se inserta una sucursal o un emisor con `empresa_id` = B, entonces la sentencia falla y no se crea nada.

16b. **Inserción propia.** Dado `restaurante_api` conectado con el contexto de A, cuando inserta un emisor con `empresa_id` = A y luego una sucursal con `empresa_id` = A que referencia ese emisor, entonces ambas inserciones tienen éxito, las filas quedan con `empresa_id` = A y se ven en el contexto de A pero no en el de B. (La base permite a la API crear emisores y sucursales de su propia empresa; qué rol de aplicación puede hacerlo se aplica en la historia 002.)

17. **Referencia cruzada.** Dado el contexto de A, cuando se inserta o actualiza una sucursal de A con `emisor_id` de un emisor de B, entonces la sentencia falla por la llave foránea compuesta, igual que con un `emisor_id` inexistente.
18. **HTTP.** Dado el resolutor de desarrollo con la empresa A: `GET /sucursales` devuelve solo sucursales de A; `GET /sucursales/{id de B}` y `PATCH /sucursales/{id de B}` responden 404 con el mismo cuerpo que un id inexistente, y la sucursal de B no cambia; `PATCH /sucursales/{id de A}` con `emisorId` de B responde 422 `EMISOR_INVALIDO`, igual que con un emisor inexistente.

### Sin contexto de empresa

19. Dada una conexión nueva de `restaurante_api` que nunca fijó el contexto con `fijar_contexto_empresa`, cuando ejecuta `SELECT` o `UPDATE` sobre `empresa`, `emisor` o `sucursal`, `DELETE` sobre `emisor` o `sucursal` (todas con filas existentes) o un `INSERT` en `emisor` o `sucursal`, entonces cada sentencia falla con SQLSTATE `42501` y un mensaje que empieza con `contexto de empresa ausente`; ninguna devuelve filas.
20. Dada una conexión de `restaurante_api` que ya tuvo contexto (fijado con `fijar_contexto_empresa`) en una transacción anterior confirmada o revertida, cuando ejecuta las mismas sentencias fuera de una transacción con contexto (sin volver a llamar `fijar_contexto_empresa`), entonces fallan igual que en el criterio 19.
21. Dado un intento de fijar el contexto con un texto que no es UUID (o vacío), sea con `fijar_contexto_empresa` (la llamada falla por la conversión a `uuid`) o solo con `set_config('app.empresa_id', …)`, cuando se consulta una tabla de empresa, entonces la consulta falla.
22. Dado código de la API que usa un modelo o servicio de empresa fuera de `ContextoEmpresa.ejecutar`, cuando se ejecuta, entonces lanza `ContextoEmpresaAusenteError` antes de enviar la consulta a la base. Esto incluye consultas crudas por la conexión de la API; la única excepción es la verificación de salud y de roles, marcada explícitamente.

22b. **`fn` no controla la transacción.** Dado código que corre dentro de `ContextoEmpresa.ejecutar`, cuando envía por la conexión de la API (consulta cruda, modelo o `queryInterface`) una sentencia que controla la transacción, es decir `COMMIT`, `ROLLBACK`, `END`, `ABORT`, `SAVEPOINT`, `RELEASE` (con o sin `SAVEPOINT`), `ROLLBACK TO`, `BEGIN`, `START TRANSACTION`, `PREPARE TRANSACTION`, `COMMIT PREPARED` o `ROLLBACK PREPARED`, en mayúsculas o minúsculas y con sus variantes (`WORK`, `TRANSACTION`, `AND CHAIN`), sola, como una de varias sentencias en el mismo texto (por ejemplo `SELECT 1; COMMIT`) o después de comentarios (`/* … */ COMMIT`, `-- …` y salto de línea), entonces la llamada lanza un error antes de que la sentencia llegue a la base. Así se mantiene el contrato de `ejecutar`: si `fn` termina bien se confirma todo lo que hizo, y si lanza (también por este rechazo) se revierte todo; nada queda confirmado ni revertido a mitad de `fn`, y la transacción sigue con el contexto de la misma empresa hasta que `ejecutar` la cierra. En cambio, un literal que contiene ese texto dentro de un valor (por ejemplo `UPDATE sucursal SET nombre = 'COMMIT; END' WHERE id = …`, también con `E'…'` o `$$…$$`) no se rechaza y se guarda tal cual. Lo mismo vale para un literal con texto como `set_config`, `SET`, `RESET` o `;` dentro de un valor (por ejemplo `UPDATE sucursal SET direccion = 'x; set y' WHERE id = …` o `SELECT … WHERE nombre = 'x; set y'`, o un nombre con el texto `set_config`): no se rechaza, la sentencia se ejecuta normalmente y el valor se guarda o se compara tal cual. El rechazo se decide sobre el texto sin literales ni comentarios. Las sentencias con las que el propio `ContextoEmpresa.ejecutar` abre, confirma o revierte su transacción no se ven afectadas.

22c. **Solo `ejecutar` autoriza una transacción.** La autorización de una transacción de la API (que sus consultas puedan llegar a la base) solo la obtiene la transacción que abre `ContextoEmpresa.ejecutar` cuando no hay un contexto activo. Dado código que corre dentro de `ContextoEmpresa.ejecutar` con la empresa A, cuando abre otra transacción en la conexión de la API (`sequelize.transaction()` anidada, gestionada o no gestionada) y fija en ella cualquier empresa, sea B o la propia A (con el mismo texto SQL que usa `ContextoEmpresa` o de cualquier otra forma), entonces esa fijación no autoriza la transacción: toda consulta enviada por ella lanza un error antes de llegar a la base, y en ningún caso devuelve filas de otra empresa ni escribe en ella. La transacción del contexto de A sigue funcionando igual. Además:
    - el texto SQL con el que `ContextoEmpresa` fija la empresa no se puede importar desde fuera de `apps/api/src/nucleo/`: un archivo de fuera que lo importe (con las formas de importación del criterio 37b) hace fallar `pnpm lint`;
    - la regla del criterio 37 sobre el texto `app.empresa_id` también detecta ese texto construido por concatenación de literales (por ejemplo `'app.' + 'empresa_id'`), y `pnpm lint` falla igual.

22d. **El contexto no se puede cambiar dentro de la transacción.** Dado código que corre dentro de `ContextoEmpresa.ejecutar` con la empresa A, cuando envía por la conexión de la API (consulta cruda, modelo o `queryInterface`) cualquier sentencia que cambie `app.empresa_id` o cualquier otro parámetro de sesión o de transacción, sea directamente (`set_config`, `SET`, `UPDATE pg_settings`…) o a través de una función que ejecuta SQL recibido como texto o por nombre de cursor (por ejemplo `SELECT ts_rewrite('x'::tsquery, 'SELECT set_config(''app.empresa_id'',''<id de B>'',true)::tsquery, ''y''::tsquery')`, aunque el SQL vaya dentro de un literal), entonces la sentencia no cambia el contexto: falla (en la API o en la base) y ninguna consulta posterior de esa misma transacción ve, modifica, borra ni crea filas de B. La defensa tiene dos capas, y cada una se verifica por separado:
    - **Guarda de la API (lista blanca).** Dentro de un contexto, por la conexión de la API solo pasan sentencias cuya primera palabra, tras quitar comentarios y en cada una de las sentencias de un texto con varias, es `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `WITH`, `VALUES` o `TABLE` (sin distinguir mayúsculas). Cualquier otra (por ejemplo `SET`, `RESET`, `ALTER`, `COPY`, `PREPARE`, `EXECUTE`, `DEALLOCATE`, `DECLARE`, `FETCH`, `MOVE`, `CLOSE`, `LISTEN`, `UNLISTEN`, `NOTIFY`, `CALL`, `DO`, `LOCK`, `ANALYZE`, `EXPLAIN`, `VACUUM`, `CREATE`, `DROP`, `GRANT`, `REVOKE`, `TRUNCATE`, `SHOW`, `DISCARD`, `LOAD`, `REFRESH`, `CLUSTER`, `REINDEX`, `CHECKPOINT`, `SECURITY LABEL`, `COMMENT`, `IMPORT`, `REASSIGN`) lanza un error antes de llegar a la base, además de lo ya rechazado por el criterio 22b. También se sigue rechazando, antes de la base, toda mención de `set_config` o `pg_settings` fuera de literales y comentarios (con o sin esquema `pg_catalog.` y también como identificador entre comillas). Los literales siguen sin decidir nada (criterio 22b): un valor con esos textos se guarda o compara tal cual. Las sentencias internas de la propia transacción no se ven afectadas: las que envía Sequelize para abrirla y cerrarla (`START TRANSACTION`, `SET TRANSACTION ISOLATION LEVEL …`, `COMMIT`, `ROLLBACK`) y la que usa `ContextoEmpresa.ejecutar` para fijar el contexto.
    - **Base de datos.** `db:preparar` quita a `PUBLIC`, `restaurante_api` y `restaurante_plataforma` el `EXECUTE` sobre las funciones de `pg_catalog` que ejecutan SQL recibido como texto o por nombre de cursor: `ts_rewrite` (todas sus firmas), `ts_stat` (todas sus firmas), `query_to_xml`, `query_to_xmlschema`, `query_to_xml_and_xmlschema`, `cursor_to_xml` y `cursor_to_xmlschema` (todas sus firmas); y el `UPDATE` sobre `pg_settings`. Dado `restaurante_api` conectado directamente por SQL, con el contexto de A fijado en su transacción, cuando llama cualquiera de esas funciones (también con el SQL de `set_config` hacia B en el texto) o hace `UPDATE pg_settings SET setting = … WHERE name = 'app.empresa_id'`, entonces cada intento falla con SQLSTATE `42501`, y después de revertir a un `SAVEPOINT` tomado antes del intento, en la misma transacción, `empresa_actual()` y `current_setting('app.empresa_id')` siguen siendo A y las tablas de empresa solo muestran filas de A. Lo mismo vale para `restaurante_plataforma` (falla por permisos). En el catálogo, ninguno de los dos roles tiene `EXECUTE` sobre esas funciones ni `UPDATE` sobre `pg_settings`. Lo deja preparado `db:preparar` junto con los criterios 38b, 38c y 38d, en las mismas bases y con el mismo comportamiento: comprueba al final que quedó aplicado, volver a ejecutarlo no falla, y si el usuario de `DATABASE_ADMIN_URL` no tiene permisos para aplicarlo, falla con un mensaje que lo dice y nombra el criterio. También se revoca la forma de `ts_rewrite` que no recibe texto (`ts_rewrite(tsquery, tsquery, tsquery)`): la aplicación no reescribe búsquedas de texto y así la regla es más simple (decisión del orquestador en la ronda 4). Esta capa exige un administrador superusuario y es una defensa adicional: desde el criterio 22e el aislamiento entre empresas ya no depende de ella. Donde el administrador no es superusuario (producción, criterio 38e), `db:preparar` con `DB_PROTECCION_CATALOGO=omitir` no la aplica y avisa; ahí estas funciones quedan cubiertas solo por la guarda (lista de nombres del criterio 38e, inciso d).
    - **Prueba observable por la API.** Dado el contexto de A, cuando `fn` intenta cada una de esas vías (una por sentencia, y también como una de varias sentencias en el mismo texto), entonces la llamada lanza un error (de la guarda o, si la guarda la dejó pasar, el `42501` de la base); si `fn` atrapa el error y sigue consultando por la misma transacción, ninguna de esas consultas devuelve, modifica ni crea filas de B (pueden fallar, por ejemplo porque la base dejó la transacción abortada, o ver solo filas de A) (comprobado desde otra conexión después de que `ejecutar` termina), y las filas de B quedan idénticas.

    Nota: `restaurante_api` conserva `EXECUTE` sobre `set_config` (es de `PUBLIC` por defecto y quitarlo exige superusuario), pero ya no lo necesita para fijar el contexto ni le sirve para cambiarlo: desde el criterio 22e la RLS no lee `app.empresa_id`, y la base garantiza que la empresa se fija una sola vez por transacción. La guarda de la API sigue siendo la primera barrera; ya no es la única.

22e. **El contexto se fija una sola vez por transacción, garantizado por la base.** La empresa de una transacción la fija la función `fijar_contexto_empresa(uuid)` y la RLS la lee con `empresa_actual()` desde la tabla interna `contexto.sesion_empresa`, atada a la sesión (`pg_backend_pid()`) y a la transacción (`pg_current_xact_id()`), a la que los roles de la aplicación no tienen acceso. `app.empresa_id` queda solo como copia para diagnóstico y la RLS no lo lee. Así, aunque una sentencia pasara la guarda de la API, un segundo intento de fijar la empresa o un `set_config('app.empresa_id', …)` (directo, por SQL dinámico o desde una función que ejecuta SQL recibido como texto) no cambia la empresa que ve la RLS. Todo lo crea una migración y no requiere superusuario. Con `restaurante_api` conectado directamente por SQL, sin la guarda:
    - **(a) `set_config` no cambia el contexto.** Dada una transacción que ejecutó `SELECT fijar_contexto_empresa(A)`, cuando luego ejecuta `SELECT set_config('app.empresa_id', '<id de B>', true)`, directo y también dentro de un bloque `DO` (con `PERFORM set_config(…)` y con `EXECUTE` de SQL dinámico que lo llama), entonces `empresa_actual()` sigue devolviendo A, `SELECT` sobre `empresa`, `emisor` y `sucursal` solo devuelve filas de A, `UPDATE` y `DELETE` sobre filas de B por id afectan 0 filas, un `INSERT` en `emisor` o `sucursal` con `empresa_id` = B falla, y desde otra conexión, al terminar, las filas de B están idénticas. (`current_setting('app.empresa_id')` sí muestra B: es solo diagnóstico.)
    - **(b) Segunda fijación.** Dada una transacción con A fijado, cuando vuelve a llamar `fijar_contexto_empresa(B)` o `fijar_contexto_empresa(A)` (directo o por SQL dinámico en un `DO`), entonces la llamada falla con SQLSTATE `42501` y un mensaje que empieza con `contexto de empresa ya fijado`; después de revertir a un `SAVEPOINT` tomado antes del intento, `empresa_actual()` sigue siendo A y las tablas de empresa solo muestran filas de A. `fijar_contexto_empresa(NULL)` falla con SQLSTATE `22004` (mensaje que empieza con `contexto de empresa inválido`) y no fija nada: en una transacción sin contexto previo, las sentencias del criterio 19 siguen fallando con `contexto de empresa ausente` (tras revertir a un `SAVEPOINT` previo al intento).
    - **(c) `set_config` sin fijación.** Dada una transacción que solo ejecutó `set_config('app.empresa_id', '<id de A>', true)`, sin `fijar_contexto_empresa`, cuando ejecuta las sentencias del criterio 19, entonces cada una falla con SQLSTATE `42501` y un mensaje que empieza con `contexto de empresa ausente`.
    - **(d) La fijación muere con la transacción.** Dada una conexión que fijó A en una transacción ya confirmada o revertida, cuando ejecuta las sentencias del criterio 19 sin volver a fijar (en una transacción nueva o en modo autocommit), entonces fallan con `contexto de empresa ausente` (criterio 20); y una transacción nueva en la misma conexión puede fijar B con `fijar_contexto_empresa` y solo ve filas de B. Dos conexiones abiertas a la vez, cada una con su empresa fijada, ven cada una solo la suya.
    - **(e) Catálogo.** El esquema `contexto` existe y su dueño es `restaurante_migrador`; ni `restaurante_api`, ni `restaurante_plataforma`, ni `PUBLIC` tienen `USAGE` ni `CREATE` sobre él, ni ningún privilegio sobre `contexto.sesion_empresa`, que es `UNLOGGED`; un `SELECT`, `INSERT`, `UPDATE` o `DELETE` directo sobre ella como `restaurante_api` falla por permisos. `restaurante_api` tiene `EXECUTE` sobre `fijar_contexto_empresa(uuid)`; `restaurante_plataforma` y `PUBLIC` no. `empresa_actual()` y `fijar_contexto_empresa(uuid)` son `SECURITY DEFINER`, su dueña es `restaurante_migrador` y tienen `search_path` fijado en su configuración a `pg_catalog, pg_temp`.
    - **(f) Por la API.** Dado el contexto de A en `ContextoEmpresa.ejecutar`, el ataque de la ronda 4 (`SELECT ts_rewrite('x'::tsquery, 'SELECT set_config(''app.empresa_id'',''<id de B>'',true)::tsquery, ''y''::tsquery')`) y el de la revisión final (un comentario `--` terminado en `\r` seguido de `SELECT set_config('app.empresa_id', '<id de B>', true)`) siguen sin ver, modificar ni crear filas de B, como en el criterio 22d; y el SQL que esos ataques intentaban ejecutar, enviado directo como en el inciso (a), no cambia el contexto, de modo que no lo cambiarían aunque pasaran la guarda. Además, la guarda rechaza antes de la base toda mención de `fijar_contexto_empresa` fuera de literales y comentarios (también con esquema `public.` o entre comillas dobles) en cualquier sentencia que no sea la fijación propia de `ContextoEmpresa.ejecutar`; un literal con ese texto se guarda o se compara tal cual (criterio 22b). Y la regla de lint de los criterios 37, 22c y 37c también vale para el texto `fijar_contexto_empresa` (sin distinguir mayúsculas, también armado con `+`, plantillas sin expresiones, `.concat()` o `.join()` de literales): fuera del servicio de contexto y de las migraciones, `pnpm lint` falla.

    `ContextoEmpresa.ejecutar` fija la empresa con `SELECT fijar_contexto_empresa($1)` como primera sentencia de su transacción, en lugar del `set_config` anterior; una llamada anidada con la misma empresa (criterio 27) no vuelve a fijar. Las revocaciones de `pg_catalog` del criterio 22d siguen como defensa adicional donde haya superusuario (ver criterio 38e para producción, sin superusuario).

23. Dada una ruta HTTP que no está marcada con `@SinEmpresa()`, cuando el resolutor de empresa no obtiene una empresa, entonces responde 401 con `{ "codigo": "EMPRESA_NO_RESUELTA" }` y el controlador no se ejecuta.

> Precisión: a nivel de base, la política falla en cuanto evalúa una fila; sobre una tabla vacía, o un filtro por índice que no encuentra filas, devuelve 0 filas sin error. En ningún caso devuelve datos. La garantía de que **toda** consulta sin contexto falla la da la API (criterio 22). Los `INSERT` sin contexto fallan siempre, también en la base.

### El contexto no se filtra entre operaciones

24. Dado un pool de la API con una sola conexión, cuando se confirma una transacción con contexto de A (fijado por `ContextoEmpresa.ejecutar` con `fijar_contexto_empresa`) y después se consulta sin contexto, entonces la consulta falla (criterio 20); y si después se abre una transacción con contexto de B, solo ve filas de B.
25. Dado lo mismo que en el criterio 24 pero con una transacción de A que termina con una excepción y se revierte, entonces el resultado es el mismo.
26. Dado un pool de la API con 2 conexiones, cuando llegan 100 peticiones HTTP concurrentes alternando las empresas A y B, y cada controlador hace dos consultas separadas por una espera asíncrona, entonces cada respuesta contiene solo datos de su empresa y `ContextoEmpresa.empresaActual()` devuelve la empresa de su petición en todo momento.
27. Dado un contexto de A activo, cuando se llama `ContextoEmpresa.ejecutar` con la empresa B, entonces lanza `ContextoEmpresaConflictoError`; si se llama con la misma empresa A, corre dentro de la transacción existente.

27b. **Después de `ejecutar` no queda contexto.** Dado código que sigue corriendo con el almacén asíncrono de un `ContextoEmpresa.ejecutar` que ya terminó, con su transacción confirmada o revertida (por ejemplo, un efecto secundario lanzado desde `fn` que, según `CLAUDE.md`, se ejecuta después de confirmar, o una promesa o temporizador que sigue vivo), cuando ese código:
    - llama `ContextoEmpresa.empresaActual()`, entonces lanza `ContextoEmpresaAusenteError`;
    - usa un modelo o servicio de empresa, o una consulta cruda por la conexión de la API, sin abrir un contexto nuevo, entonces lanza `ContextoEmpresaAusenteError` antes de enviar la consulta (criterio 22);
    - llama `ContextoEmpresa.ejecutar` con la misma empresa o con otra, entonces se abre una transacción nueva con el contexto pedido y funciona: no lanza `ContextoEmpresaConflictoError` ni `ContextoEmpresaAusenteError`, y solo ve filas de esa empresa;
    - llama `OperacionPlataforma.ejecutar` (o `consultar`), entonces funciona y no lanza `OperacionPlataformaAnidadaError`.

    Lo mismo vale para el código que sigue corriendo con el almacén de un `OperacionPlataforma.ejecutar` (o `consultar`) que ya terminó: puede llamar `OperacionPlataforma.ejecutar` o `ContextoEmpresa.ejecutar` y ambos funcionan; no queda dentro de una operación de plataforma.
28. Dado un contexto de empresa activo, cuando se llama `OperacionPlataforma.ejecutar`, entonces lanza `OperacionPlataformaAnidadaError`. Dada una operación de plataforma en curso, cuando su código usa un servicio o modelo de empresa de la API, entonces lanza `ContextoEmpresaAusenteError`; la conexión de plataforma nunca atiende consultas de la API ni al revés.

### Empresa de la petición: punto de enganche para la historia 002

29. Dado `NODE_ENV=production` y `EMPRESA_POR_HEADER=habilitado`, cuando arranca la API, entonces no arranca y el registro explica que esa opción está prohibida en producción.

29b. **`NODE_ENV` obligatorio.** Dado que `NODE_ENV` no está definido (o está vacío), cuando arranca la API, entonces no arranca y el registro explica que falta `NODE_ENV` y cuáles son sus valores válidos (`development`, `test` y `production`); así un despliegue que olvide `NODE_ENV=production` no queda con el resolutor por cabecera. Con cualquier otro valor tampoco arranca, con el mismo tipo de mensaje. Además, `db:preparar` (y todo lo que derive contraseñas de los roles) solo usa contraseñas por defecto cuando `NODE_ENV` es `development` o `test` de forma explícita: sin `NODE_ENV` o con `production`, si falta alguna `DB_PASSWORD_*` falla con un mensaje que nombra la variable que falta y no crea ni modifica roles.
30. Dado `NODE_ENV=production` sin `EMPRESA_POR_HEADER`, cuando llega `GET /sucursales` con la cabecera `x-empresa-id` de una empresa real, entonces responde 401 `EMPRESA_NO_RESUELTA` (la cabecera se ignora).
31. Dado `NODE_ENV` `development` o `test` con `EMPRESA_POR_HEADER=habilitado`, cuando llega una petición con `x-empresa-id` = UUID válido, entonces la petición corre con ese contexto; si la cabecera falta o no es un UUID, responde 401 `EMPRESA_NO_RESUELTA`.

### Operaciones de plataforma y auditoría

32. Dado que no hay contexto de empresa, cuando se llama `PlataformaEmpresasService.registrarEmpresa(datos, { actor, motivo })` con datos válidos, entonces se crean en una sola transacción la empresa, sus emisores y sus sucursales, y una fila en `auditoria_plataforma` con el actor, la operación `registrar_empresa`, el motivo, el `empresa_id` creado y el detalle de lo creado.

32b. **La operación no cierra su propia transacción.** Dada una llamada a `OperacionPlataforma.ejecutar` cuya `fn` intenta confirmar o revertir la transacción por su cuenta (`commit()` o `rollback()` sobre la transacción recibida, sentencias SQL `COMMIT`, `ROLLBACK`, `END` o `ABORT` enviadas por la transacción, o cualquier otra vía que confirme datos fuera del cierre que hace `ejecutar`), cuando se ejecuta, entonces la operación falla con un error y, al terminar, no queda en la base ningún cambio hecho por `fn` sin su fila en `auditoria_plataforma` (lo normal es que no quede nada). Lo mismo vale para `OperacionPlataforma.consultar` (lectura de plataforma sin auditoría): su `fn` no puede confirmar ninguna escritura; si lo intenta, la llamada falla y la escritura no queda en la base.
33. Dado `actor` o `motivo` vacíos o solo con espacios, cuando se llama cualquier operación de plataforma, entonces lanza un error de validación y no se crea nada, tampoco la fila de auditoría.
34. Dados datos inválidos (RUC con dígito verificador incorrecto, RUC repetido en la entrada, RUC ya registrado, sucursal que referencia un RUC que no está en la entrada, código de establecimiento que no tiene 4 dígitos, dos sucursales del mismo emisor con el mismo código, hora de corte o WhatsApp mal formados), cuando se llama `registrarEmpresa`, entonces lanza un error de validación que indica el campo, y no queda nada creado ni auditado.
35. Dada una empresa existente, cuando se llaman `PlataformaEmpresasService.agregarEmisor` o `agregarSucursal`, entonces se crea el registro en esa empresa y se audita con la operación `agregar_emisor` o `agregar_sucursal`.

35b. **Hora de corte por defecto.** Dada una sucursal sin `horaCorte` en la entrada de `registrarEmpresa` o de `agregarSucursal`, cuando se crea, entonces queda con hora de corte `05:00` (y `sucursalRespuesta.horaCorte` es `"05:00"`). Lo mismo ocurre si `restaurante_api`, con el contexto de A, inserta por SQL una sucursal de A sin la columna `hora_corte`. La hora de corte se puede cambiar después con `PATCH` (criterio 39).

36. Dados los roles, cuando `restaurante_plataforma` intenta `UPDATE`, `DELETE` o `TRUNCATE` sobre `auditoria_plataforma`, entonces falla; y cuando `restaurante_api` intenta leer o escribir `auditoria_plataforma`, también falla.
37. Dado el código de la API, cuando un archivo fuera de `apps/api/src/modulos/plataforma/` importa la conexión de plataforma, o un archivo distinto del servicio de contexto escribe el texto `app.empresa_id`, entonces `pnpm lint` falla.

37b. **Alcance de la regla de lint.** Las dos reglas del criterio 37 se aplican a todo archivo TypeScript de `apps/api/src` con extensión `.ts`, `.tsx`, `.mts` o `.cts` (y `pnpm lint` los incluye a todos). La regla de la conexión de plataforma detecta, fuera de `apps/api/src/modulos/plataforma/`, además del `import` estático: el `import()` dinámico, `require(...)` (también `import x = require(...)`) y los reexportes (`export * from`, `export { … } from`, `export * as … from`) del módulo de la conexión de plataforma. En cada uno de esos casos `pnpm lint` falla.

37c. **Texto del parámetro armado con métodos.** Dado un archivo de `apps/api/src` distinto del servicio de contexto (y fuera de las migraciones), cuando arma el texto `app.empresa_id` (sin distinguir mayúsculas) solo a partir de literales:
    - con `.concat()` sobre un literal, con uno o varios argumentos literales y en cadena (por ejemplo `'app.'.concat('empresa_id')`, `'app'.concat('.', 'empresa_id')`, `'app.'.concat('empresa').concat('_id')`);
    - con `.join()` sobre un arreglo de literales, con separador literal (también vacío) o sin argumento, en cuyo caso el separador es la coma como en JavaScript (por ejemplo `['app.', 'empresa_id'].join('')`, `['app', 'empresa_id'].join('.')`);
    - o combinando esas formas entre sí o con `+` y plantillas sin expresiones (criterio 22c),

    entonces `pnpm lint` falla con el mismo mensaje que el criterio 37. En el servicio de contexto y en las migraciones esas formas siguen permitidas. La regla de lint es una ayuda para quien escribe código, no la barrera: un texto armado con valores que no son literales (variables, llamadas a otras funciones) queda fuera de su alcance, y lo detiene la guarda en tiempo de ejecución (criterios 22b, 22c y 22d).

### Catálogo: la regla vale para las tablas futuras

38. Dada la base migrada, cuando se inspecciona el catálogo, entonces:
    - toda tabla del esquema `public`, salvo `migraciones`, tiene RLS activada **y forzada**;
    - toda tabla con columna `empresa_id`, más `empresa`, tiene una política para `restaurante_api` que usa `empresa_actual()` tanto en `USING` como en `WITH CHECK`;
    - `restaurante_api` y `restaurante_plataforma` no tienen privilegios `TRUNCATE`, `REFERENCES` ni `TRIGGER` sobre ninguna tabla, ni `CREATE` sobre ningún esquema;
    - toda llave foránea entre dos tablas con `empresa_id` incluye `empresa_id` en sus columnas;
    - `restaurante_api` no tiene ningún privilegio sobre `migraciones` ni `auditoria_plataforma`.

    Esta prueba recorre el catálogo, así que una tabla nueva sin RLS hace fallar la suite.

38b. **Texto de consultas ajenas.** Todas las conexiones de la API comparten el rol `restaurante_api` (y las de plataforma, `restaurante_plataforma`), y el texto de una consulta puede llevar valores de otra empresa. Dadas dos sesiones abiertas con el mismo rol (por ejemplo, una con contexto de A ejecutando una consulta y otra con contexto de B), cuando una consulta `pg_stat_activity`, `pg_stat_get_activity(...)` o `pg_stat_get_backend_activity(...)`, entonces no obtiene el texto de la consulta de la otra sesión (la llamada falla por permisos o el campo no trae el texto). Además, ni `restaurante_api` ni `restaurante_plataforma` son miembros de `pg_read_all_stats` ni de `pg_monitor`. Lo deja preparado `db:preparar` (o la migración) en la base `restaurante` y en la de pruebas, y volver a ejecutarlo no falla; si el usuario de `DATABASE_ADMIN_URL` no tiene permisos para aplicarlo, `db:preparar` falla con un mensaje que lo dice, en vez de dejar la base sin esta protección, salvo que se pida de forma explícita omitirla con `DB_PROTECCION_CATALOGO=omitir` (criterio 38e).

38c. **Cancelar, terminar o enumerar sesiones ajenas.** Como todas las conexiones de la API comparten el rol `restaurante_api` (y las de plataforma, `restaurante_plataforma`), PostgreSQL deja por defecto que una sesión cancele o termine a otra del mismo rol, aunque atienda a otra empresa. Dadas dos sesiones abiertas con el mismo rol (por ejemplo, una con contexto de A y otra con contexto de B), cuando una de ellas:
    - llama `pg_cancel_backend(pid)` o `pg_terminate_backend(pid)` (en todas sus firmas) con el pid de la otra, entonces la llamada falla por permisos y la otra sesión sigue viva y termina su consulta normalmente;
    - llama cualquiera de las funciones `pg_stat_get_backend_*` (por ejemplo `pg_stat_get_backend_idset`, `pg_stat_get_backend_pid`, `pg_stat_get_backend_userid`, `pg_stat_get_backend_start`, `pg_stat_get_backend_activity_start` o `pg_stat_get_backend_xact_start`), entonces la llamada falla por permisos y no obtiene pid, usuario ni tiempos de otras sesiones.

    En el catálogo, ni `restaurante_api` ni `restaurante_plataforma` tienen `EXECUTE` sobre `pg_cancel_backend`, `pg_terminate_backend` ni ninguna función `pg_stat_get_backend_*`, y no son miembros de `pg_signal_backend`. Lo deja preparado `db:preparar` junto con el criterio 38b, en las mismas bases y con el mismo comportamiento: volver a ejecutarlo no falla, y si el usuario de `DATABASE_ADMIN_URL` no tiene permisos para aplicarlo, falla con un mensaje que lo dice (salvo con `DB_PROTECCION_CATALOGO=omitir`, criterio 38e).

38d. **Objetos grandes (large objects).** Los objetos grandes de PostgreSQL no tienen RLS ni `empresa_id`, y todas las conexiones de la API comparten rol, así que servirían para guardar o leer datos entre empresas. Dados `restaurante_api` (con o sin contexto de empresa) y `restaurante_plataforma` conectados, cuando intentan crear, leer, escribir, borrar o enumerar objetos grandes, es decir llamar `lo_create`, `lo_creat`, `lo_from_bytea`, `lo_get`, `lo_put`, `lo_open`, `loread`, `lowrite`, `lo_lseek`, `lo_lseek64`, `lo_tell`, `lo_tell64`, `lo_close`, `lo_truncate`, `lo_truncate64`, `lo_unlink`, `lo_import` o `lo_export` (en todas sus firmas), o hacer `SELECT` sobre `pg_largeobject` o `pg_largeobject_metadata`, entonces cada intento falla por permisos y no crea, cambia ni devuelve nada. En el catálogo, ninguno de los dos roles tiene `EXECUTE` sobre ninguna función de `pg_catalog` cuyo nombre empiece con `lo_` ni sobre `loread` o `lowrite`, ni `SELECT` sobre `pg_largeobject` o `pg_largeobject_metadata`. Lo deja preparado `db:preparar` junto con los criterios 38b y 38c, en las mismas bases y con el mismo comportamiento: volver a ejecutarlo no falla, y si el usuario de `DATABASE_ADMIN_URL` no tiene permisos para aplicarlo, falla con un mensaje que lo dice (salvo con `DB_PROTECCION_CATALOGO=omitir`, criterio 38e).

38e. **PostgreSQL sin superusuario (producción).** Decisión del usuario: en producción PostgreSQL será administrado, sin superusuario (DigitalOcean Managed u otro similar). Las protecciones del catálogo (criterios 38b, 38c, 38d y la capa de base del 22d) exigen un administrador superusuario; el aislamiento entre empresas (RLS y criterio 22e) no, porque lo crean las migraciones con `restaurante_migrador`. Por eso `db:preparar` tiene un modo explícito sin esas protecciones, y la guarda de la API (y la de plataforma) las cubre por nombre en todos los entornos.
    - **(a) Comprobación previa.** `db:preparar` comprueba, antes de crear o modificar roles o bases, si el usuario de `DATABASE_ADMIN_URL` puede aplicar las protecciones del catálogo: puede si es superusuario o si tiene los privilegios del dueño de los objetos de `pg_catalog` afectados (en la práctica, solo un superusuario). Si puede, las aplica y comprueba exactamente como hoy (criterios 38b, 38c, 38d y 22d), haya o no `DB_PROTECCION_CATALOGO`: con superusuario, `DB_PROTECCION_CATALOGO=omitir` no cambia nada y no se escribe el aviso del inciso (c).
    - **(b) Sin opción explícita.** Si no puede y `DB_PROTECCION_CATALOGO` no está definida (o está vacía), `db:preparar` falla antes de crear o modificar roles o bases (la base de destino no se crea), con un mensaje que dice que el administrador no puede aplicar las protecciones del catálogo, nombra los criterios 38b, 38c, 38d y 22d, y explica que con `DB_PROTECCION_CATALOGO=omitir` se prepara la base sin ellas y que entonces quedan solo en la guarda de la API.
    - **(c) Con `DB_PROTECCION_CATALOGO=omitir`.** Si no puede, `db:preparar` aplica todo lo demás igual que con superusuario (roles con sus atributos del criterio 7 y sus contraseñas, la base con dueño `restaurante_migrador` y sus privilegios de base; los privilegios del esquema, la RLS y el criterio 22e los crean las migraciones y no requieren superusuario), no aplica las protecciones del catálogo, termina bien (código de salida 0) y escribe un aviso que nombra cada protección omitida: texto de consultas ajenas (38b), cancelar, terminar o enumerar sesiones ajenas (38c), objetos grandes (38d) y la capa de base de SQL desde texto y `pg_settings` (22d); y dice que en esa base esas protecciones quedan solo en la guarda de la API (y en la de plataforma). El aviso se escribe en cada ejecución, por la salida de error de `pnpm db:preparar` y por la opción `avisar` de `prepararBaseDeDatos` (ver "Interfaces de la API"); volver a ejecutar no falla. Si la base ya tenía las protecciones de una preparación anterior con superusuario, siguen ahí (no se deshacen), pero no se comprueban. Después, `db:migrar` sobre esa base termina sin errores. Cualquier otro valor de `DB_PROTECCION_CATALOGO` (por ejemplo `omitirr` u `OMITIR`) hace fallar `db:preparar` antes de crear o modificar nada, con un mensaje que nombra la variable y su único valor válido (`omitir`), haya o no superusuario.
    - **(d) Guarda por nombre (vale siempre, haya o no superusuario).** Dentro de `ContextoEmpresa.ejecutar`, la guarda de la API rechaza antes de enviarla a la base (con un error que no es `DatabaseError`) toda sentencia que mencione, fuera de literales y comentarios, alguno de estos nombres, sin distinguir mayúsculas, solo o calificado con esquema (`pg_catalog.lo_get`) y también como identificador entre comillas dobles (`"lo_get"`, `"pg_catalog"."pg_stat_activity"`):
        - **Nombres completos:** `pg_stat_activity`, `pg_stat_get_activity`, `pg_cancel_backend`, `pg_terminate_backend`, `pg_signal_backend`, `pg_largeobject`, `pg_largeobject_metadata`, `loread`, `lowrite`, además de los que ya rechaza: `set_config`, `pg_settings`, `ts_rewrite`, `ts_stat` y `fijar_contexto_empresa` (salvo la fijación propia de `ContextoEmpresa.ejecutar`, criterio 22e).
        - **Prefijos:** `pg_stat_get_backend_` (todas las funciones `pg_stat_get_backend_*`), `lo_` (todas las funciones de objetos grandes: `lo_get`, `lo_put`, `lo_from_bytea`, `lo_create`, `lo_creat`, `lo_open`, `lo_unlink`, `lo_import`, `lo_export`, `lo_truncate`, `lo_truncate64`, `lo_lseek`, `lo_lseek64`, `lo_tell`, `lo_tell64`, `lo_close`…), además de los que ya rechaza: `query_to_xml` y `cursor_to_xml` (y sus variantes `*schema` y `*_and_xmlschema`). También `table_to_xml`, `schema_to_xml` y `database_to_xml` (con sus variantes): leen una relación nombrada dentro de un literal (por ejemplo `schema_to_xml('pg_catalog', true, false, '')` incluye `pg_stat_activity`, y `table_to_xml('pg_largeobject_metadata', …)` enumera los objetos grandes), así que sin ellos un nombre de la lista se podría esconder en un literal.
        - **Límites de identificador.** Un carácter de identificador es una letra `A`–`Z` o `a`–`z`, un dígito, `_`, `$` o cualquier carácter desde U+0080 (como en el escáner de PostgreSQL). Un nombre completo se rechaza si el carácter anterior y el siguiente no son de identificador; un prefijo, si el carácter anterior no lo es (cualquier continuación cuenta). El carácter anterior se mira en el texto sin literales ni comentarios, de modo que `.` (esquema), `"`, espacios, paréntesis y operadores son límites. Así **pasan**, por ejemplo, los alias `my_lo_get`, `colo_r`, `xlo_get`, `pg_stat_activity_x`, `loreadx` y `mi_pg_largeobject` (son otros identificadores; un nombre completo con sufijo nombra otro objeto, que no existe en `pg_catalog`), y **se rechaza** cualquier identificador que empiece con `lo_` o `pg_stat_get_backend_`, también un alias como `lo_x` (convención: ninguna tabla, columna ni alias de la aplicación empieza con `lo_`).
        - Un identificador con escapes Unicode (`U&"…"`) se sigue rechazando siempre, como hoy, porque podría escribir cualquiera de estos nombres (por ejemplo `U&"\006Co_get"`).
        - Los literales (`'…'`, `E'…'`, `$$…$$`) y los comentarios con estos textos no deciden nada: se guardan o se comparan tal cual (criterio 22b).

      `restaurante_plataforma` no pasa por la guarda de la API: la guarda de su conexión aplica la misma lista de nombres (incluidos los que ya rechazaba la guarda de la API y el texto `app.empresa_id`), con los mismos límites y el mismo rechazo de `U&"…"`, a toda consulta dentro de `OperacionPlataforma.ejecutar` y de `consultar` (para `fijar_contexto_empresa` sin excepción); el rechazo es un error que no es `DatabaseError`, la operación falla y no queda en la base ningún cambio de `fn` ni su fila de auditoría (criterio 32b).
    - **(e) Pruebas observables.**
        - **Guarda de la API:** dentro de `ContextoEmpresa.ejecutar(A)`, una sentencia por cada nombre y prefijo de la lista (por ejemplo `SELECT query FROM pg_stat_activity`, `SELECT * FROM pg_stat_get_activity(NULL)`, `SELECT pg_stat_get_backend_pid(1)`, `SELECT pg_cancel_backend(1)`, `SELECT pg_terminate_backend(1)`, `SELECT 1 FROM pg_largeobject`, `SELECT oid FROM pg_largeobject_metadata`, `SELECT lo_create(0)`, `SELECT lo_from_bytea(0, '\x00')`, `SELECT lo_get(1)`, `SELECT loread(0, 1)`, `SELECT lowrite(0, '\x00')`, `SELECT table_to_xml('pg_largeobject_metadata', true, false, '')`, `SELECT schema_to_xml('pg_catalog', true, false, '')`), también con `pg_catalog.`, entre comillas dobles, en mayúsculas, tras otra sentencia permitida en el mismo texto y tras comentarios, lanza un error que no es `DatabaseError`; después, en la misma transacción, un `SELECT` sobre `sucursal` sigue funcionando y solo devuelve filas de A (prueba de que la sentencia no llegó a la base). Controles que funcionan: `SELECT 1 AS my_lo_get, 2 AS colo_r, 3 AS pg_stat_activity_x, 4 AS loreadx`, un `UPDATE sucursal SET direccion = 'lo_get pg_stat_activity pg_terminate_backend' WHERE id = …` (el valor se guarda tal cual) y un `SELECT` precedido de un comentario con esos nombres.
        - **Guarda de plataforma:** lo mismo dentro de `OperacionPlataforma.ejecutar` y `consultar`, con un muestreo de nombres y prefijos que incluya al menos uno de cada grupo (38b, 38c, 38d, `table_to_xml`/`schema_to_xml`, y los anteriores `set_config`, `ts_rewrite`, `query_to_xml`, `fijar_contexto_empresa`): cada uno lanza un error que no es `DatabaseError`, y en `ejecutar` no queda ningún cambio de `fn` ni fila de auditoría; los mismos controles funcionan.
        - **`db:preparar` sin superusuario:** con el superusuario de las pruebas se crea un rol temporal `LOGIN CREATEROLE CREATEDB NOSUPERUSER`, dueño de nada en `pg_catalog`, con `ADMIN OPTION` sobre los tres roles de la aplicación (como el administrador de un PostgreSQL administrado que los creó), y se usa como administrador sobre una base temporal. Sin `DB_PROTECCION_CATALOGO`, `db:preparar` falla con un mensaje que contiene `DB_PROTECCION_CATALOGO=omitir` y nombra 38b, 38c, 38d y 22d, y la base temporal no existe. Con un valor inválido, falla nombrando la variable. Con `DB_PROTECCION_CATALOGO=omitir`, termina bien; el aviso nombra 38b, 38c, 38d y 22d y menciona la guarda de la API; ejecutarlo otra vez no falla; los roles siguen cumpliendo el criterio 7; `db:migrar` sobre esa base termina sin errores; y en esa base, como `restaurante_api` por SQL directo, el aislamiento sigue intacto: con `fijar_contexto_empresa(A)` solo se ven filas de A en `empresa`, `emisor` y `sucursal`, `UPDATE`/`DELETE` de filas de B por id afectan 0 filas, `INSERT` con `empresa_id` de B falla, sin contexto las sentencias del criterio 19 fallan con `contexto de empresa ausente`, `set_config('app.empresa_id', B, true)` no cambia `empresa_actual()` y una segunda fijación falla con `contexto de empresa ya fijado` (incisos a y b del criterio 22e).
        - **`db:preparar` con superusuario y `omitir`:** sobre una base auxiliar, con el administrador superusuario de las pruebas y `DB_PROTECCION_CATALOGO=omitir`, las protecciones se aplican igual (por ejemplo, `restaurante_api` no tiene `EXECUTE` sobre `lo_get(oid)` ni `SELECT` sobre `pg_stat_activity`, y no tiene `EXECUTE` sobre ninguna firma de `ts_rewrite`) y no se escribe el aviso de omisión.

### Sucursal: configuración (RF-02) y reglas puras

39. Dado el contexto de A, cuando se llama `PATCH /sucursales/{id}` con cambios válidos de emisor, código de establecimiento, nombre, dirección, horario, WhatsApp u hora de corte, entonces responde 200 con la sucursal actualizada y `actualizadoEn` cambia; los campos no enviados no cambian.
40. Dado el contexto de A, cuando el `PATCH` trae datos mal formados, entonces responde 400 `DATOS_INVALIDOS` con la lista de campos; si el código de establecimiento ya lo usa otra sucursal del mismo emisor, o el nombre ya lo usa otra sucursal de la empresa, responde 409 `CONFLICTO`.

40b. **Carácter NUL y cuerpos grandes.** Dado un texto con el carácter NUL (U+0000) en cualquier campo de texto, cuando llega en `PATCH /sucursales/:id`, entonces responde 400 `DATOS_INVALIDOS` indicando el campo, y la sucursal no cambia; cuando llega en la entrada de `registrarEmpresa`, `agregarEmisor` o `agregarSucursal` (incluidos `actor` y `motivo`), entonces lanza el error de validación del criterio 34 indicando el campo, y no queda nada creado ni auditado. En ningún caso el texto se guarda alterado (sin el NUL, truncado o reemplazado) ni la respuesta es 500. Dado un cuerpo de petición mayor a 100 KB, cuando llega a cualquier ruta, entonces responde 413 con `{ "codigo": "CUERPO_DEMASIADO_GRANDE", "mensaje" }`, nunca 500, y no se ejecuta el controlador.

40c. **Sustitutos UTF-16 sueltos y JSON mal formado.** Igual que con el NUL (criterio 40b): dado un texto con un sustituto UTF-16 sin pareja (un sustituto alto o bajo suelto, por ejemplo `\ud800` o `\udc00`, escrito como escape en el JSON) en cualquier campo de texto, cuando llega en `PATCH /sucursales/:id`, entonces responde 400 `DATOS_INVALIDOS` indicando el campo y la sucursal no cambia; cuando llega en la entrada de `registrarEmpresa`, `agregarEmisor` o `agregarSucursal` (incluidos `actor` y `motivo`), entonces lanza el error de validación del criterio 34 indicando el campo, y no queda nada creado ni auditado. En ningún caso el texto se guarda alterado (por ejemplo, con el carácter de reemplazo U+FFFD) ni la respuesta es 500. Un par de sustitutos válido (un carácter fuera del plano básico, como un emoji) se acepta y se guarda tal cual. Dado un cuerpo JSON mal formado en cualquier ruta, cuando llega, entonces responde 400 `DATOS_INVALIDOS` con un mensaje genérico, que no repite el texto del analizador de JSON (ni fragmentos del cuerpo, ni posiciones), y no se ejecuta el controlador.

40d. **Errores 4xx.** Dada cualquier ruta, cuando la petición termina en un error con código HTTP 4xx, sea lanzado por un guard, un pipe, un interceptor, un controlador o un servicio, por el enrutador (ruta inexistente) o por el analizador de cuerpos antes de llegar a Nest, entonces la respuesta conserva ese código HTTP, su cuerpo es `{ codigo, mensaje }` (más `campos` donde ya corresponde) y nunca es 500:
    - Los errores propios de la aplicación conservan su código y su mensaje: por ejemplo 401 `EMPRESA_NO_RESUELTA` (criterio 23), 404 `NO_ENCONTRADO` de una sucursal inexistente o ajena y 422 `EMISOR_INVALIDO` (criterio 18). 400, 409 y 413 siguen respondiendo `DATOS_INVALIDOS`, `CONFLICTO` y `CUERPO_DEMASIADO_GRANDE` (criterios 40, 40b y 40c).
    - Los demás 4xx: 401 → `NO_AUTENTICADO`; 403 → `PROHIBIDO`; 404, incluida una ruta o un método sin ruta (por ejemplo `GET /no-existe`) → `NO_ENCONTRADO`; 405 → `METODO_NO_PERMITIDO`; 415 → `TIPO_NO_SOPORTADO`, incluido el que lanza el analizador de cuerpos por un charset o una codificación de contenido no soportados (por ejemplo `PATCH /sucursales/:id` con `Content-Type: application/json; charset=iso-8859-1`, o con `Content-Encoding` no soportado), que no es una `HttpException`; 429 → `DEMASIADAS_PETICIONES`; cualquier otro 4xx (por ejemplo 406, 408, 410 o 418) → `PETICION_INVALIDA`.
    - Para esos códigos el mensaje es un texto genérico fijo por código: no repite el mensaje de la excepción, ni la ruta, el método, el cuerpo, el charset o la codificación, ni detalles internos (por ejemplo, `GET /no-existe` no devuelve `Cannot GET /no-existe`).
    - Cuando el error ocurre antes del controlador (ruta inexistente, analizador de cuerpos, guard), el controlador no se ejecuta.
    - Solo los errores no controlados (cualquier excepción que no sea un 4xx) responden 500 `ERROR_INTERNO` con un mensaje genérico. Las respuestas que un controlador arma por su cuenta, como el 503 de `GET /health` (criterio 6), no cambian.
41. `validarRuc` (en `packages/dominio`) acepta RUC de 11 dígitos con prefijo 10, 15, 16, 17 o 20 y dígito verificador correcto (por ejemplo `20100000009`, `20600000005`, `10456789019`) y rechaza el resto (por ejemplo `20100000000`, `2010000000`, `30100000001`, `2010000000a`).
42. `diaOperativo(instante, horaCorte)` (en `packages/dominio`) devuelve la fecha `AAAA-MM-DD` del día operativo en hora de Lima: con corte `05:00`, `2026-03-10T03:00-05:00` da `2026-03-09`, `2026-03-10T05:00-05:00` da `2026-03-10` y `2026-01-01T02:00-05:00` da `2025-12-31`; con corte `00:00`, siempre da la fecha calendario de Lima.

## Casos límite

- Contexto fijado con `fijar_contexto_empresa` y un UUID válido de una empresa que no existe: las consultas devuelven 0 filas y los `INSERT` fallan por llave foránea; no es un error de contexto.
- Revertir a un `SAVEPOINT` tomado antes de `fijar_contexto_empresa` deshace la fijación: la transacción vuelve a quedar sin contexto y puede fijar una empresa de nuevo, pero nunca ve dos empresas a la vez. Por la API no aplica, porque `fn` no puede usar `SAVEPOINT` (criterio 22b).
- La fila de `contexto.sesion_empresa` de una sesión que ya terminó puede quedar en la tabla, y un proceso nuevo puede reutilizar su `pid`: como la `xid` de esa fila es de una transacción terminada (y las `xid8` no se repiten), no da contexto a nadie y la siguiente fijación la reemplaza.
- Una transacción de la API de solo lectura (`SET TRANSACTION READ ONLY`) o en una réplica de solo lectura no puede fijar el contexto, porque fijarlo escribe en `contexto.sesion_empresa`. Hoy ninguna lo es; ver "Riesgos" en `plan.md`.
- Una petición con contexto que lanza una excepción: la transacción se revierte, el contexto desaparece con ella y la conexión vuelve limpia al pool.
- Peticiones concurrentes con `Promise.all` dentro de un mismo controlador: todas usan la misma transacción y el mismo contexto.
- Operaciones fuera de HTTP (colas, WebSockets, tareas programadas de historias futuras): deben envolver su trabajo en `ContextoEmpresa.ejecutar`; sin eso fallan por el criterio 22.
- Efectos secundarios que corren después de confirmar (imprimir, enviar al PSE, avisos en tiempo real): aunque hereden el almacén asíncrono de la petición, ya no tienen contexto (criterio 27b); si necesitan leer o escribir datos de la empresa, abren su propio `ContextoEmpresa.ejecutar`.
- Mensajes de error: un 404 o 422 por un recurso de otra empresa no se distingue de uno inexistente (mismo código, mismo mensaje).
- Unicidad global del RUC: un intento de registrar un RUC que ya usa otra empresa revela que el RUC existe en el sistema. En esta historia solo la plataforma registra emisores, pero desde la historia 002 el Administrador de una empresa también podrá hacerlo, así que el aviso le llegará a un usuario de empresa. Como el padrón de RUC es público, se acepta (decisión del usuario).
- `DELETE` de una sucursal o emisor referenciado por otras filas: falla por llave foránea; esta historia no ofrece borrados por la API.
- Horario con tramos que cruzan la medianoche (por ejemplo, 18:00 a 02:00): se acepta; `hasta` menor que `desde` significa el día siguiente. Un tramo con `desde` igual a `hasta`, o dos tramos solapados el mismo día, se rechazan.
- Sucursal sin `horaCorte` en el alta: queda con `05:00` (criterio 35b). Una `horaCorte` enviada pero mal formada sigue siendo un error de validación (criterios 34 y 40).
- Sucursal sin WhatsApp: se acepta; el campo es opcional y en `PATCH` se puede quitar con `null`.
- Cambio de emisor de una sucursal: en esta historia se permite siempre (criterio 39), porque todavía no existen comprobantes.

## Reglas de negocio aplicables

- Una empresa tiene uno o varios emisores (RUC); cada sucursal pertenece a una empresa y a uno de sus emisores, y tiene su código de establecimiento SUNAT (RF-01, RF-02, HU-01).
- Los emisores y las sucursales los crean el superadministrador y también el Administrador, este último solo dentro de su propia empresa (decisión del usuario). La regla de rol se aplica en la historia 002; en esta historia la base ya permite a la API crear emisores y sucursales de su propia empresa (criterio 16b).
- El RUC tiene 11 dígitos, prefijo 10, 15, 16, 17 o 20 y dígito verificador correcto. Cada RUC pertenece a una sola empresa del sistema (decisión del usuario). No se valida todavía la relación entre el régimen Nuevo RUS y el RUC de persona natural.
- El emisor guarda su régimen tributario, que define qué comprobantes puede emitir (en el Nuevo RUS, solo boletas). En esta historia solo se guarda; la restricción se aplica en la historia de facturación (RF-65).
- No se puede cambiar el emisor (RUC) de una sucursal que ya emitió comprobantes (decisión del usuario). El bloqueo lo implementa la historia de facturación; en esta historia el cambio se permite porque aún no hay comprobantes.
- El nombre de la sucursal no se repite dentro de la empresa, sin distinguir mayúsculas.
- El horario de la sucursal es una lista de tramos por día de la semana (varios por día), que pueden cruzar la medianoche, y puede quedar vacío. Los feriados y las excepciones por fecha quedan para más adelante.
- El WhatsApp de la sucursal es un celular peruano (`+51 9XXXXXXXX`) y es opcional.
- Cada sucursal tiene una hora de corte del día operativo; las ventas de madrugada cuentan para el día anterior (documento de diseño). Por defecto es `05:00` y se puede modificar; a la hora de corte exacta empieza el nuevo día (decisión del usuario).
- Los datos de una empresa nunca se comparten con otra (RNF-06, regla de delivery sobre datos de clientes).
- Toda operación del superadministrador queda registrada en una auditoría que no se puede modificar (RNF-09, RF-07).
- Identificadores UUID en todas las tablas (documento de diseño).

## Contrato

### Paquetes compartidos

- `packages/dominio`: `validarRuc(ruc: string): boolean`, `diaOperativo(instante: Date, horaCorte: string): string`, `validarHorario(tramos: TramoHorario[]): ResultadoValidacion` y el tipo `RegimenTributario` = `'NUEVO_RUS' | 'RER' | 'MYPE_TRIBUTARIO' | 'GENERAL'`.
- `packages/contratos` (zod, con tipos inferidos):
  - `horaSchema`: texto `HH:MM`, de `00:00` a `23:59`.
  - `tramoHorarioSchema`: `{ dia: 1..7 (1 = lunes, ISO), desde: hora, hasta: hora }`.
  - `horarioSchema`: arreglo de tramos validado con `validarHorario`; puede estar vacío (sucursal sin horario cargado).
  - `whatsappSchema`: celular peruano en formato E.164, `^\+519\d{8}$`.
  - `rucSchema`, `codigoEstablecimientoSchema` (`^\d{4}$`), `regimenTributarioSchema`.
  - `emisorEntradaSchema`: `{ ruc, razonSocial (1..200), regimen }`.
  - `sucursalEntradaSchema`: `{ rucEmisor, nombre (1..100), codigoEstablecimiento, direccion (1..300), horario (opcional, por defecto []), whatsapp (opcional), horaCorte (opcional, por defecto '05:00') }`.
  - `registrarEmpresaEntradaSchema`: `{ nombre (1..150), emisores: emisorEntrada[] (mínimo 1), sucursales: sucursalEntrada[] (mínimo 1) }`, con RUC únicos y cada `rucEmisor` presente en `emisores`.
  - `sucursalConfigurarEntradaSchema`: parcial de `{ emisorId (uuid), nombre, codigoEstablecimiento, direccion, horario, whatsapp (o null para quitarlo), horaCorte }`, con al menos un campo.
  - `sucursalRespuestaSchema`: `{ id, empresaId, emisorId, nombre, codigoEstablecimiento, direccion, horario, whatsapp | null, horaCorte (HH:MM), creadoEn, actualizadoEn (ISO 8601) }`.
  - `saludRespuestaSchema` y `errorRespuestaSchema`: `{ codigo, mensaje, campos? }`.
  - Códigos de error (`CODIGOS_ERROR`): `DATOS_INVALIDOS`, `EMPRESA_NO_RESUELTA`, `NO_ENCONTRADO`, `CONFLICTO`, `EMISOR_INVALIDO`, `CUERPO_DEMASIADO_GRANDE`, `NO_AUTENTICADO`, `PROHIBIDO`, `METODO_NO_PERMITIDO`, `TIPO_NO_SOPORTADO`, `DEMASIADAS_PETICIONES`, `PETICION_INVALIDA` y `ERROR_INTERNO` (criterio 40d).

### Endpoints

| Método y ruta | Contexto | Entrada | Respuestas |
| --- | --- | --- | --- |
| `GET /health` | `@SinEmpresa()` | — | 200 `saludRespuesta`; 503 si la base no responde |
| `GET /sucursales` | empresa | — | 200 `sucursalRespuesta[]`; 401 `EMPRESA_NO_RESUELTA` |
| `GET /sucursales/:id` | empresa | `id` UUID | 200 `sucursalRespuesta`; 400 `DATOS_INVALIDOS` si `id` no es UUID; 404 `NO_ENCONTRADO`; 401 |
| `PATCH /sucursales/:id` | empresa | `sucursalConfigurarEntrada` | 200 `sucursalRespuesta`; 400 `DATOS_INVALIDOS`; 404 `NO_ENCONTRADO`; 409 `CONFLICTO`; 413 `CUERPO_DEMASIADO_GRANDE`; 422 `EMISOR_INVALIDO`; 401 |

- Cualquier ruta responde 413 `CUERPO_DEMASIADO_GRANDE` si el cuerpo supera 100 KB (criterio 40b).
- Todo error 4xx de cualquier ruta (también de una ruta inexistente) conserva su código HTTP con `{ codigo, mensaje }` según el criterio 40d; solo los errores no controlados responden 500 `ERROR_INTERNO`.

- En esta historia no hay endpoints HTTP de plataforma: crear empresas exige identificar al superadministrador, y eso llega con la historia 002. La vía de plataforma se usa desde la semilla y las pruebas.

### Interfaces de la API (contratos públicos para las pruebas)

- `ContextoEmpresa` (`apps/api/src/nucleo/contexto-empresa/`):
  - `ejecutar<T>(empresaId: string, fn: () => Promise<T>): Promise<T>`: valida el UUID, abre una transacción en la conexión de la API, ejecuta `SELECT fijar_contexto_empresa($1)` con `empresaId` como primera sentencia (criterio 22e; si la llamada es anidada con la misma empresa, reutiliza la transacción y no vuelve a fijar) y corre `fn` con el contexto en el `AsyncLocalStorage`. Confirma si `fn` termina bien y revierte si lanza. `fn` no puede controlar la transacción por SQL (criterio 22b), ni autorizar otra transacción de la API (criterio 22c), ni cambiar el contexto o parámetros de sesión dentro de su transacción: por la conexión de la API solo pasan `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `WITH`, `VALUES` y `TABLE`, y nunca una mención fuera de literales de `set_config`, `pg_settings`, `fijar_contexto_empresa` ni de los demás nombres de la lista del criterio 38e (criterios 22d, 22e y 38e). Al terminar, el contexto termina también para el código que siga corriendo con ese almacén asíncrono (criterio 27b).
  - `empresaActual(): string`: lanza `ContextoEmpresaAusenteError` si no hay contexto, también después de que `ejecutar` terminó (criterio 27b).
  - Errores: `ContextoEmpresaAusenteError`, `ContextoEmpresaConflictoError`.
- `RESOLUTOR_EMPRESA` (token de Nest) con la interfaz `ResolutorEmpresa { resolver(peticion): Promise<string | null> }`. En esta historia hay dos implementaciones: `ResolutorEmpresaNulo` (siempre `null`; es la de producción) y `ResolutorEmpresaPorCabecera` (lee `x-empresa-id`; solo si `NODE_ENV` es `development` o `test` y `EMPRESA_POR_HEADER=habilitado`). La historia 002 agrega la suya, que tomará la empresa del usuario autenticado, y la registra en el mismo token.
- `ContextoEmpresaInterceptor` (global): si la ruta no tiene `@SinEmpresa()`, pide la empresa al resolutor, responde 401 si es `null`, y corre el controlador dentro de `ContextoEmpresa.ejecutar`. Los guards de Nest corren antes que los interceptores, así que el guard de autenticación de 002 podrá dejar la empresa en la petición para que su resolutor la lea.
- `OperacionPlataforma` (`apps/api/src/modulos/plataforma/`): `ejecutar<T>({ actor, motivo, operacion, empresaId? }, fn: (tx) => Promise<T>): Promise<T>`. Usa la conexión de `restaurante_plataforma`, abre una transacción, corre `fn` con la transacción explícita e inserta la fila de auditoría en esa misma transacción antes de confirmar: o quedan el cambio y su auditoría, o no queda nada. `fn` no puede confirmar ni revertir la transacción por su cuenta (criterio 32b). `consultar<T>(fn: (tx) => Promise<T>): Promise<T>`: lectura de plataforma sin auditoría; la transacción siempre se revierte y `fn` tampoco puede confirmarla (criterio 32b). En ambos, la conexión de plataforma rechaza los nombres de la lista del criterio 38e. Error: `OperacionPlataformaAnidadaError`.
- `PlataformaEmpresasService`: `registrarEmpresa(datos, auditoria)`, `agregarEmisor(empresaId, datos, auditoria)`, `agregarSucursal(empresaId, datos, auditoria)`, `listarEmpresas()`. `auditoria` es `{ actor: string, motivo: string }`. `registrarEmpresa` devuelve `{ empresaId, emisores: { id, ruc }[], sucursales: { id, nombre }[] }`.
- `SucursalService` (contexto de empresa): `listar()`, `obtener(id)` (devuelve `null` si no existe o es de otra empresa) y `configurar(id, cambios)`.
- `prepararBaseDeDatos(opciones)` (`apps/api/scripts/lib/preparar-bd.ts`, lo que corre `pnpm db:preparar`): `{ adminUrl?, baseDeDatos?, recrear?, env?, registrar?, avisar? }`. `env` es de donde lee `NODE_ENV`, `DB_PASSWORD_*` y `DB_PROTECCION_CATALOGO`; `avisar(mensaje)` recibe el aviso de protecciones omitidas (criterio 38e; por defecto, la salida de error). Lanza un error si la preparación falla.

### Funciones de la base de datos (contratos públicos para las pruebas a nivel SQL)

- `public.fijar_contexto_empresa(p_empresa uuid) RETURNS void` (criterio 22e): fija la empresa de la transacción en curso. Solo `restaurante_api` la puede ejecutar. Falla con `42501` `contexto de empresa ya fijado` si la transacción ya fijó una empresa (la misma u otra) y con `22004` `contexto de empresa inválido` si recibe `NULL`. Un texto que no es UUID falla al convertirse a `uuid`, antes de entrar en la función. También deja `app.empresa_id` con el mismo valor, solo para diagnóstico.
- `public.empresa_actual() RETURNS uuid`: la empresa fijada en la transacción en curso; si no hay, falla con `42501` `contexto de empresa ausente`. La usan las políticas de RLS; ignora `app.empresa_id`.

## Cambios al modelo de datos

Todas las tablas usan UUID (`gen_random_uuid()` por defecto) y `creado_en`, `actualizado_en` (`timestamptz`, no nulos).

- **Esquema `contexto`** (criterio 22e): interno, dueño `restaurante_migrador`, sin `USAGE` ni `CREATE` para `restaurante_api`, `restaurante_plataforma` ni `PUBLIC`.
- **`contexto.sesion_empresa`** (`UNLOGGED`): `pid integer PRIMARY KEY`, `xid xid8 NOT NULL`, `empresa_id uuid NOT NULL`. Una fila por sesión de la base, que solo vale para la transacción cuya `xid` guarda. Sin RLS (no está en `public` y nadie más que su dueño la toca) y sin privilegios para los roles de la aplicación; solo la leen y escriben las dos funciones siguientes, que corren como su dueña.
- **Función `fijar_contexto_empresa(p_empresa uuid) RETURNS void`** (`public`, `VOLATILE`, `SECURITY DEFINER`, dueña `restaurante_migrador`, `SET search_path = pg_catalog, pg_temp`, no `STRICT`): si `p_empresa` es `NULL`, lanza SQLSTATE `22004` `contexto de empresa inválido`. Si no, inserta `(pg_backend_pid(), pg_current_xact_id(), p_empresa)` con `ON CONFLICT (pid) DO UPDATE … WHERE` la fila existente es de otra transacción (`xid` distinta); si ya había una fila de esta misma transacción (no se insertó ni actualizó nada), lanza SQLSTATE `42501` `contexto de empresa ya fijado`, aunque sea la misma empresa. Al final fija `app.empresa_id` con `set_config(…, true)`, solo para diagnóstico. `EXECUTE` solo para `restaurante_api` (revocado a `PUBLIC`).
- **Función `empresa_actual()`** (`public`, `STABLE`, `SECURITY DEFINER`, dueña `restaurante_migrador`, `SET search_path = pg_catalog, pg_temp`): devuelve la `empresa_id` de la fila de `contexto.sesion_empresa` con `pid = pg_backend_pid()` y `xid = pg_current_xact_id_if_assigned()`; si no hay, lanza SQLSTATE `42501` con el mensaje `contexto de empresa ausente`. Ignora `app.empresa_id`. `EXECUTE` solo para `restaurante_api`.
- **`empresa`**: `id`, `nombre` (texto, 1 a 150).
- **`emisor`**: `id`, `empresa_id` (FK `empresa`), `ruc` (`char(11)`, único en todo el sistema), `razon_social` (1 a 200), `regimen` (texto con `CHECK` en `NUEVO_RUS`, `RER`, `MYPE_TRIBUTARIO`, `GENERAL`). Único `(id, empresa_id)` para las llaves compuestas. Índice por `empresa_id`.
- **`sucursal`**: `id`, `empresa_id` (FK `empresa`), `emisor_id`, `nombre` (1 a 100), `codigo_establecimiento` (`char(4)`, `CHECK ~ '^\d{4}$'`), `direccion` (1 a 300), `horario` (`jsonb`, no nulo, por defecto `[]`), `whatsapp` (texto nulo, `CHECK ~ '^\+519\d{8}$'`), `hora_corte` (`time`, no nulo, `DEFAULT '05:00'`). FK compuesta `(emisor_id, empresa_id)` → `emisor (id, empresa_id)`. Únicos `(emisor_id, codigo_establecimiento)` y `(empresa_id, lower(nombre))`. Índice por `empresa_id`.
- **`auditoria_plataforma`**: `id`, `ocurrido_en` (`timestamptz`, por defecto `now()`), `actor` (texto libre no vacío; en 002 pasa a ser el id del superadministrador), `operacion` (texto no vacío), `motivo` (texto no vacío), `empresa_id` (uuid nulo, FK `empresa`), `detalle` (`jsonb`). Un trigger rechaza `UPDATE` y `DELETE`, y otro rechaza `TRUNCATE`.
- **RLS**: `ENABLE` y `FORCE ROW LEVEL SECURITY` en las cuatro tablas.
  - Política `aislamiento_empresa` `TO restaurante_api` en `emisor` y `sucursal`: `USING (empresa_id = (SELECT empresa_actual())) WITH CHECK (empresa_id = (SELECT empresa_actual()))`; en `empresa`, lo mismo con `id`.
  - Política `acceso_plataforma` `TO restaurante_plataforma` en `empresa`, `emisor`, `sucursal` y `auditoria_plataforma`: `USING (true) WITH CHECK (true)`.
  - `restaurante_migrador` no tiene política: como la RLS está forzada, no ve filas. Las migraciones hacen DDL; una migración de datos futura que necesite recorrer todas las empresas debe quitar y volver a poner `FORCE` dentro de su propia transacción (ver `plan.md`).
- **Base de datos**: dueña `restaurante_migrador`; se revocan `CONNECT`, `CREATE` y `TEMPORARY` a `PUBLIC`; `CONNECT` para `restaurante_api` y `restaurante_plataforma`; solo `USAGE` sobre `public`.
- **Convención para las tablas futuras**: `empresa_id uuid not null` con FK a `empresa`, índice por `empresa_id`, RLS activada y forzada, política `aislamiento_empresa`, llaves foráneas compuestas con `empresa_id`, privilegios explícitos en la misma migración y nunca `TRUNCATE`. El criterio 38 lo verifica.

## Fuera de alcance

- Autenticación, usuarios, roles, PIN y equipos vinculados (historia 002), incluido el resolutor de empresa definitivo y los endpoints de plataforma por HTTP.
- La PWA (`apps/app`), la carta web (`apps/web`), el puente Android y `packages/ui`.
- Suscripciones, planes y módulos por sucursal (RF-03 a RF-07). El alta de empresa (`registrarEmpresa`, `agregarSucursal`) **no** crea la suscripción: la sucursal nace sin suscripción, y la creación de la suscripción llega con RF-03, cuya historia extenderá `registrarEmpresa`.
- Feriados y excepciones del horario por fecha (para más adelante).
- Validar que un emisor del Nuevo RUS tenga RUC de persona natural.
- Bloquear el cambio de emisor de una sucursal que ya emitió comprobantes (historia de facturación).
- Endpoints HTTP para crear emisores y sucursales (llegan con 002, junto con la regla de rol).
- La tasa de IGV con vigencia del emisor y la restricción de comprobantes por régimen: van en la historia de cálculo de montos y facturación. Motivo: (1) nada en esta historia la usa; (2) decidir qué tasa aplica a una fecha es cálculo de montos, ruta crítica que merece sus propias pruebas primero; (3) la tasa aplicable está pendiente de validar con el contador (18 % o la tasa reducida para restaurantes MYPE); (4) agregarla después es una tabla nueva, sin reescribir datos.
- Datos del emisor que pedirá la facturación (domicilio fiscal, ubigeo, nombre comercial) y el slug de la carta web.
- Colas (pg-boss), WebSockets, Sentry, despliegue y staging.
- Claves de idempotencia. `PATCH /sucursales/:id` asigna valores absolutos y repetirlo da el mismo resultado. `registrarEmpresa` y `agregarEmisor` no llevan clave porque la unicidad global del RUC rechaza el reintento con un error de validación (400), y `agregarSucursal` tampoco, por la unicidad del nombre de la sucursal dentro de la empresa. Las claves de idempotencia llegan con las primeras escrituras que no tengan una unicidad natural que rechace el reintento.

## Notas para otras historias

- **Historia 002 (autenticación):**
  - Aplicar la regla de rol para crear emisores y sucursales: Superadministrador y Administrador de su propia empresa (ver "Permisos").
  - Unir `auditoria_plataforma` a la auditoría general del módulo de seguridad.
  - El `actor` de la auditoría pasa de texto libre al id del superadministrador.
  - `ResolutorEmpresaPorCabecera` queda solo para las pruebas automáticas: permitirlo únicamente con `NODE_ENV=test` (deja de valer `development`).
- **Historia de facturación:** bloquear el cambio de emisor (RUC) de una sucursal que ya emitió comprobantes; aplicar la restricción de comprobantes por régimen (RF-65).
- **Historia de suscripciones (RF-03):** el alta de empresa y de sucursal debe crear la suscripción.
- **Historias de tiempo real (Socket.IO con adaptador PostgreSQL) y de colas (pg-boss):** hoy `restaurante_api` puede usar `LISTEN`/`NOTIFY` y advisory locks (`pg_advisory_lock` y similares) sin restricción, y esos canales y bloqueos son globales a la base, no a la empresa. Al introducir Socket.IO y pg-boss, revisar que los nombres de canal, las cargas de `NOTIFY` y las llaves de los bloqueos no sirvan de canal lateral entre empresas (por ejemplo, que una empresa no pueda escuchar el canal de otra ni deducir actividad ajena por un bloqueo), y decidir si se restringen o se separan por empresa. No se corrige en esta historia porque aún no hay ningún uso. En la misma revisión: `pg_locks` y `pg_blocking_pids` siguen al alcance de `restaurante_api` y exponen metadatos de actividad de otras sesiones del mismo rol (pids, tablas y filas bloqueadas, tipo de bloqueo), aunque no datos de filas; decidir si se restringen cuando lleguen las colas y el tiempo real.
- **Despliegue (dónde alojar PostgreSQL), decidido:** en producción PostgreSQL será administrado, sin superusuario (DigitalOcean Managed u otro similar; decisión del usuario, criterio 38e). El aislamiento entre empresas (RLS más la fijación única del contexto del criterio 22e) lo crean las migraciones con `restaurante_migrador` y **no** requiere superusuario. Las protecciones del catálogo de los criterios 38b, 38c y 38d y la capa de base del 22d sí lo requieren: en producción `db:preparar` se corre con `DB_PROTECCION_CATALOGO=omitir`, las omite con un aviso, y esos objetos quedan cubiertos solo por la guarda de la API y la de plataforma (lista de nombres del criterio 38e). La historia de despliegue debe: definir `DB_PROTECCION_CATALOGO=omitir` en el entorno de producción; no instalar en la base de la aplicación extensiones que expongan actividad, datos o SQL dinámico al rol de la API (por ejemplo `pg_stat_statements`, `dblink` o `postgres_fdw`), o, si alguna se instala, agregar sus nombres a la lista de la guarda; y no conceder a los roles de la aplicación membresías en roles predefinidos (`pg_monitor`, `pg_read_all_stats`, `pg_signal_backend`), que sin superusuario `db:preparar` no puede quitar.
